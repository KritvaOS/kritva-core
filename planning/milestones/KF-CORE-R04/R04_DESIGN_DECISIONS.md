# KF-CORE-R04 — Design Decisions (architecture consult, 04-10-2026)

Recorded from the architecture review session before R04-001 implementation. These approve the API direction; each requirement still enters the authoritative `REQUIREMENTS.md` only when its implementing task is accepted.

**Scope sentence (milestone and release gate):** R0.4 establishes platform contracts and integration boundaries; it does not implement a concrete Linux, RTOS, MCU, vendor, Nexus, or Edge platform adapter.

| # | Decision | Outcome |
|---|---|---|
| Q1 | Shared `Callback` vocabulary (`types/callback.hpp`): `function` (non-null when a callback is required; null is invalid) and `context` (null is valid), opaque, non-owning, caller-owned | Approved. The generic type carries no "must not block" rule; each callback-bearing service states who invokes it, where it may run, whether it may block, allocate, throw or re-enter, the context lifetime, and what happens at stop/destruction. Callback functions shall not throw (documented; the function-pointer type is not changed for this). |
| Q2 | Breaking `ITimer` change: `Result<void> start(Duration period, TimerMode mode, Callback callback)` (preferred over `set_callback()`) | Approved. `period > 0`; `function != nullptr`; `context == nullptr` valid; start while running = `INVALID_STATE`; `stop()` while stopped = success/no-op; `stop()` while running is synchronous and does not return until a currently executing callback has returned; no callback is invoked after a successful `stop()`; `stop()` from the callback = `INVALID_STATE`; one-shot: exactly once after a successful start unless stopped first, then the timer is stopped; periodic: zero or more invocations until `stop()`; execution context adapter-defined; no Core-owned timer thread; no clock domain on timers; jitter/overrun policy adapter-defined. |
| Q3 | Watchdog | Keep the three methods; no `state()`. `start` requires timeout > 0 (`INVALID_ARGUMENT`); `start` while running = `INVALID_STATE`; `kick` while not running = `INVALID_STATE`; `stop` while stopped = success/no-op; `kick()` never restarts an expired or stopped watchdog; expiry behavior is adapter-defined, Core guarantees nothing about continued execution, and expiry never triggers Runtime recovery. |
| Q4 | `IPlatformAdapter` / `PlatformInfo` / `PlatformService` | Approved: `info()`, `supports()`, non-owning `scheduler()`/`clock()`/`timer()`/`watchdog()`, `capabilities()`. `supports(s) == false` iff the service pointer is `nullptr` (both directions). `PlatformInfo {name, version}` only, immutable from the adapter's perspective, no CPU/OS/board/vendor fields. No Core-reserved capability-id range; an adapter must not reinterpret an existing Core capability identity. |
| Q5 | `RuntimeManager::attach_platform(IPlatformAdapter&)` and `platform() const noexcept` | Authorized R0.4 extension of the frozen R0.3 class: setup-only (allowed before the topology freeze, `INVALID_STATE` after), stores a non-owning reference, does not probe the adapter (no call to `scheduler()`, `clock()`, `timer()`, `watchdog()` or `capabilities()`), and `initialize`/`start`/`stop`/`shutdown`/`reset` never touch platform services. Mandatory proof: a differential test shows the full R0.3 integration scenario set is identical (state transitions, invocation traces, errors, fault state, recovery, statistics) with and without an attached adapter. |
| Q6 | `DependencyGraph` and runtime lifecycle semantics unchanged; numbering `CORE-PLAT-004..011` | Approved. No renumbering of `CORE-PLAT-001..003`. |

Ownership rule: the integrator owns the adapter and every service it exposes; `RuntimeManager` owns nothing and stores a non-owning reference; the adapter must outlive any attachment; no `shared_ptr`, `unique_ptr`, singleton or service locator.
