# KF-CORE-R05 — API Design Decisions (Q1–Q9)

Approved by the independent reviewer (ChatGPT) on 04-10-2026, before implementation. These refine `R05_DESIGN_DECISIONS.md` (D1–D12) with concrete API shapes. All R05 production API is **additive**: no R0.4 signature changes (`IPlatformAdapter`, `IScheduler`, `IClock`, `ITimer`, `IWatchdog`, `RuntimeManager::attach_platform()`, `RuntimeManager::platform()`).

| # | Decision | Approved shape |
|---|---|---|
| Q1 | `PlatformContext` | `platform/context.hpp`; small copyable value view over one nullable non-owning `IPlatformAdapter*`; default = unattached; `PlatformContext() noexcept`, `explicit PlatformContext(IPlatformAdapter&) noexcept`, `explicit PlatformContext(IPlatformAdapter*) noexcept`; `attached()`, `const PlatformInfo* info()` (nullptr when unattached), `scheduler()/clock()/timer()/watchdog()` (nullptr when unattached or unsupported), `supports(PlatformService)` (false when unattached), `capabilities()` snapshot by value (empty when unattached), `has_capability(CapabilityId)` using the existing `CapabilitySet::contains`. Calls the adapter on demand, caches nothing, owns nothing, no static/global state, no name/version inference. |
| Q2 | No `RuntimeManager` change in R05-001 | The integrator builds the context from an adapter or from `runtime.platform()`. |
| Q3 | Requirement model | `platform/requirements.hpp`; `enum class Requirement { REQUIRED, OPTIONAL }`; declarative `PlatformRequirements` with `add_service()` and `add_capability()` returning `Result<void>`: `INVALID_ARGUMENT` for an invalid (zero) `CapabilityId` or an unknown service enumerator. **Duplicate detection is by service identity or `CapabilityId` identity, not by (item, level)**: `add_service(SCHEDULER, REQUIRED)` then `add_service(SCHEDULER, OPTIONAL)` is `INVALID_ARGUMENT`; no silent upgrade or downgrade; failures are atomic. `PlatformRequirementReport evaluate(...)` is the authoritative structured result (missing required/optional services and capabilities, declaration order, services before capabilities, `satisfied()`); `Result<void> check_required(...)` is `UNSUPPORTED` when not satisfied and its message identifies the first missing required declaration, but consumers must never need to parse the message. Evaluation has no side effects. |
| Q4 | Explicit consumption | `Result<IScheduler*> require_scheduler()`, `Result<time::IClock*> require_clock()`, `Result<time::ITimer*> require_timer()`, `Result<IWatchdog*> require_watchdog()` on `PlatformContext`: success is the adapter-owned pointer, failure is `UNSUPPORTED` when unattached or unsupported; they never start, stop, configure, create or own a service. Platform service errors are never translated or wrapped by Core: a service's own `Error` stays its own; a Component that propagates one sets `source = info().id()` per the existing Component contract. No error-wrapping helper is added. R0.4 callback, lifetime and re-entry rules are unchanged. |
| Q5 | R05-004 | Contract text in `runtime_manager.hpp` plus tests; no new Runtime API, no behavior change, no change to the lifecycle state machine. Acceptable under the exact commit message `feat(core): preserve runtime platform lifecycle boundary`. |
| Q6 | Capability matching | By `CapabilityId == CapabilityId` only (hard acceptance criterion). Never platform name or version, capability version, string matching, vendor or OS inference. |
| Q7 | Atomicity | A rejected declaration leaves the requirements object semantically unchanged. |
| Q8 | Test-target isolation | Two layers: (1) a static audit that nothing under `include/`, `src/` or the production CMake targets includes `tests/`, `reference_platform` or other test doubles; (2) build isolation: the production library builds without test sources and the reference platform is compiled only by test targets. |
| Q9 | Copyable value | `PlatformContext` is copyable; the contract states that copying a `PlatformContext` does not extend the lifetime of the adapter and does not transfer or duplicate ownership. |

Numbering is unchanged: CORE-PLAT-012 (R05-001), 013 (R05-002), 014 (R05-003), 015 (R05-004), 016 (R05-005), 017 (R05-006), 018 (R05-007). A requirement becomes authoritative in `REQUIREMENTS.md` only when its implementing task is accepted.
