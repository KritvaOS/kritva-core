# Kritva Core Requirements R0.4

## P0
- CORE-GEN-001 Platform-independent foundation.
- CORE-GEN-002 C++20.
- CORE-GEN-003 No ROS2/DDS/EtherCAT/vendor dependency.
- CORE-GEN-004 Public APIs under include/kritva/core.
- CORE-GEN-005 Independently testable without physical hardware.
- CORE-LIF-002 Define lifecycle transition behavior.
- CORE-LIF-003 Reject invalid lifecycle transitions.
- CORE-CFG-002 Provide a validation path for configuration.
- CORE-PLAT-001 Define scheduler platform contract: TaskConfig field semantics (priority is implementation-independent and relative with no Core-defined range, cpu_affinity is a bit mask where 0 means unconstrained, period 0 means aperiodic), non-owning context and entry lifetime, create_task registers inactive tasks while stopped with dynamic creation while running left to the adapter, idempotent start/stop, opaque TaskId with 0 invalid and unique among existing tasks, and atomic reported (not thrown) failures.
- CORE-PLAT-002 Define clock platform contract.
- CORE-PLAT-003 Define watchdog platform contract.
- CORE-PLAT-004 Define the platform adapter boundary: platform contracts are implemented outside kritva-core and Core production sources include no operating-system, RTOS, vendor, hardware-driver, ROS 2/DDS or EtherCAT interface (enforced by the repository audit); the integrator owns every adapter and service, Core holds only non-owning references, creates and destroys no platform object, and has no singleton, global platform or service locator, and a platform object must outlive every Core object that references it; the shared Callback type carries a function (null is invalid where a callback is required) and an opaque, non-owning, caller-owned context (null is valid) that Core never dereferences, with callback execution context, blocking, re-entrancy and context lifetime stated by each service and callback functions never throwing; adapters report failure through Result/Error with INVALID_ARGUMENT, INVALID_STATE, UNSUPPORTED, RESOURCE_UNAVAILABLE and TIMEOUT meaning, atomically; thread safety is adapter-defined and Core makes no real-time guarantee through a platform contract.
- CORE-PLAT-005 Harden the scheduler platform contract (platform::IScheduler) without implementing a scheduler: TaskId 0 is invalid and ids are unique among a scheduler's tasks; a failed create_task is atomic and consumes no id; TaskConfig priority is relative with an adapter-defined mapping, cpu_affinity 0 means unconstrained and a non-zero mask is honoured or refused (INVALID_ARGUMENT for a malformed mask, UNSUPPORTED when affinity cannot be provided), period 0 is aperiodic, positive is periodic and negative is INVALID_ARGUMENT; create_task registers inactive tasks while stopped and dynamic creation while running is adapter policy (supported, or INVALID_STATE with no effect); start is idempotent and all-or-nothing, stop is idempotent and synchronous; an entry is invoked only while the scheduler is running and never after stop has returned, never concurrently with itself, never throws, and never calls stop() on its own scheduler (INVALID_STATE instead of self-waiting); the context is caller-owned, non-owning and valid until stop has returned; resource exhaustion is reported as RESOURCE_UNAVAILABLE without abort or exception; teardown requires an orderly stop before task resources are released; thread safety is adapter-defined; the scheduler makes no hard-real-time, latency or jitter guarantee and has no recovery behavior that affects the Runtime.
- CORE-PLAT-006 Define the timer platform contract (time::ITimer) without implementing a timer: a timer measures elapsed time on a monotonic base, independent of IClock and the REALTIME domain, and carries no ClockDomain; start(period, mode, callback) is valid only while the timer is stopped and is atomic, failing with no effect as INVALID_ARGUMENT (period zero or negative, or null callback function; a null context is valid), INVALID_STATE (already running, including a call from the timer's own callback), UNSUPPORTED (mode or period the adapter cannot provide) or RESOURCE_UNAVAILABLE; a ONE_SHOT timer invokes its callback exactly once no earlier than one period after start and is then stopped and restartable, a PERIODIC timer invokes it until stop with adapter-defined accuracy, jitter and overrun handling and never overlaps invocations; stop is idempotent and synchronous (when it returns no callback is executing or will begin) and fails with INVALID_STATE instead of self-waiting when called from the timer's own callback; the callback is invoked by the adapter, never throws and is short and non-blocking by default, the context is opaque, non-owning, caller-owned and valid until stop has returned (or a one-shot callback has returned); the adapter documents resolution and maximum period; teardown requires an orderly stop; thread safety is adapter-defined; the timer makes no hard-real-time, latency or jitter guarantee and its expiry never triggers Runtime recovery.
- CORE-PLAT-007 Define the watchdog platform contract (platform::IWatchdog) without implementing a watchdog: a watchdog is STOPPED (initial) or RUNNING; start(timeout) is valid only while stopped, begins the first timeout window and fails with no effect as INVALID_ARGUMENT (timeout zero or negative), INVALID_STATE (already running; a running watchdog is never silently reconfigured), UNSUPPORTED (timeout outside the adapter's range or resolution) or RESOURCE_UNAVAILABLE; kick restarts the timeout window and is valid only while running, failing with INVALID_STATE and no effect otherwise and never starting the watchdog; stop is idempotent, returns a running watchdog to stopped, and an adapter that cannot disable its watchdog fails with UNSUPPORTED leaving it running; a restart carries nothing over from the previous activation; the expiry action is adapter-defined and outside Core, and expiry never triggers RuntimeManager::reset() or any Runtime recovery, Core never kicks, starts or stops a watchdog on the caller's behalf and requires no background worker; failures use Result/Error atomically and never throw; the integrator owns the watchdog and Core holds only non-owning references; thread safety and the contexts permitted to kick are adapter-defined; no hard-real-time, latency or jitter guarantee is made.
- CORE-PLAT-008 Define the platform adapter contract (platform::IPlatformAdapter, PlatformInfo, PlatformService) for minimal platform identity, service discovery and capability reporting without implementing any platform: PlatformInfo carries only a name and a Version (no CPU, operating-system, board or vendor field or type) and info() returns it immutably, equal on every call and valid until the adapter is destroyed; scheduler(), clock(), timer() and watchdog() each return a non-owning pointer to an adapter-owned service object that is stable for the adapter's life, or nullptr meaning "not supported", never an error and never a placeholder; supports(service) is non-virtual and is true exactly when the matching accessor is non-null, false for nullptr and for an unknown enumerator; capabilities() returns an owned snapshot of the existing CapabilitySet that is deterministic (same entries in the same order unless documented otherwise), where capability identities are adapter-chosen, Core reserves no identity range and an adapter does not give an identity a different meaning; capability reporting and service queries never start a service, instantiate hardware, activate a feature or change Runtime behavior; the integrator owns the adapter and its services, Core holds only non-owning references and introduces no singleton, global adapter, adapter registry or service locator; thread safety is adapter-defined and no real-time guarantee is made.
- CORE-PLAT-009 Provide a reusable platform conformance suite (tests/platform/) that a future external adapter runs against its own scheduler, clock, timer, watchdog and platform adapter: it uses only public Core headers and the standard library, runs without hardware, network or vendor SDK, reports failures through a Report instead of aborting, checks only the mandatory Core semantics defined by CORE-PLAT-001 to CORE-PLAT-008 and CORE-TIME-001 and CORE-TIME-002 (argument validation, state transitions and idempotency, error codes, atomic failure, no entry or callback outside the permitted window, re-entrancy, identity, discovery and capability determinism), accepts every outcome the contracts leave adapter-defined (affinity, priority range, capacity, dynamic task creation, supported timer modes and resolution, watchdog timeout range and whether it can be stopped) and records a skip rather than a failure where an adapter legitimately cannot provide a feature, and is itself validated by running it against conforming reference adapters under different adapter policies and by requiring it to reject deliberately faulty scheduler, timer, watchdog, clock and adapter test doubles; no production API is added to support the suite.
- CORE-PLAT-010 Define the Runtime-platform integration boundary as an additive, optional extension of runtime::RuntimeManager: attach_platform(IPlatformAdapter&) stores a non-owning reference and platform() returns it or nullptr; attachment is a setup operation valid only until the first successful initialize() fixes the topology and only while no adapter is attached, otherwise it fails with INVALID_STATE and changes nothing, an attached adapter is never silently replaced and there is no detach; attachment calls no member of the adapter and no other Runtime operation ever calls the adapter or starts, stops or kicks a scheduler, timer or watchdog, reads a clock or creates a thread or task, so that every result, state, invocation order, error, fault, recovery and statistic of the frozen R0.3 Runtime is identical with and without an attached adapter (proven by a differential test); the integrator owns the adapter and its services and the Runtime never owns, copies, moves or destroys them and has no singleton, global adapter or service locator; a platform failure reaches the Runtime only through a Component written by the integrator and is propagated unchanged by the existing failure semantics, a watchdog expiry never enters the Runtime and a Runtime FAULT never starts or stops a watchdog; runtime_manager.hpp only forward-declares the adapter and no platform header or implementation enters Runtime production code; no existing R0.3 signature or semantic changes.
- CORE-PLAT-011 Validate the R0.4 platform abstraction release candidate as a deliverable: a fresh clone builds in Debug and Release with no warnings and passes the complete CTest suite, AddressSanitizer and UndefinedBehaviorSanitizer, ThreadSanitizer where configured, strict compiler diagnostics and GCC -fanalyzer; coverage is reviewed against the R0.3 baseline; the requirements traceability audit reports zero errors; the installed package is consumed by an external project at the version recorded in VERSION and CMakeLists.txt, including a platform adapter attached to the installed RuntimeManager; VERSION and the CMake project version agree at 0.4.0; no operating-system, RTOS, vendor, threading or logging dependency and no platform implementation is present in the production sources; and the production code is unchanged between the Platform Integration Freeze (apart from the reviewed additive RuntimeManager platform attachment) and the release candidate.
- CORE-PLAT-012 Define platform::PlatformContext (platform/context.hpp) as a small, copyable, non-owning value view over one nullable IPlatformAdapter, built from an adapter reference or a nullable adapter pointer (so RuntimeManager::platform() can be passed directly) and unattached by default: it owns, creates and destroys nothing, holds no state beyond one pointer, caches nothing, is not a service registry or service locator and has no static or global state; copying it copies the view and neither extends the adapter's lifetime nor transfers or duplicates ownership; the integrator owns the adapter and every service and the adapter must outlive every context and every pointer obtained through one; scheduler(), clock(), timer() and watchdog() forward to the adapter and return its non-owning, stable pointer or nullptr when unattached or unsupported, supports() is true exactly when the accessor is non-null and false when unattached or for an unknown enumerator, info() returns the adapter's identity or nullptr when unattached, capabilities() returns an owned snapshot (empty when unattached) and has_capability() is decided by capability identity alone and never by any name or version; no query starts, stops, configures or creates a service or changes Runtime behavior; IPlatformAdapter semantics and every R0.4 signature are unchanged and no RuntimeManager change is made.
- CORE-PLAT-013 Define platform service requirement semantics (platform/requirements.hpp) using capability identity: a copyable, declarative PlatformRequirements lists platform services and capabilities as REQUIRED or OPTIONAL in an observable declaration order, and add_service() and add_capability() fail atomically with INVALID_ARGUMENT for an unknown service or level, an invalid (zero) CapabilityId or a duplicate decided by service or capability identity rather than by the pair with its level, with no silent upgrade, downgrade or merge; a capability requirement is satisfied exactly when the platform reports a capability with that CapabilityId and a service requirement exactly when PlatformContext::supports() is true, and no platform name or version, capability name or version, string matching or vendor or operating-system inference is ever used; evaluate() returns the authoritative structured PlatformRequirementReport of every missing required and optional service and capability in declaration order, never fails, treats an unattached context as providing nothing, is deterministic, queries only supports() once per declared service and capabilities() at most once, and never starts, stops, configures or creates a service or changes the requirements, the context, the adapter or the Runtime; check_required() succeeds when no REQUIRED item is missing (optional items never matter) and otherwise fails with UNSUPPORTED naming the first missing required declaration (services before capabilities, then declaration order) in a message that consumers need not parse; existing CapabilitySet semantics, IPlatformAdapter and every R0.4 signature are unchanged.
- CORE-PLAT-014 Define explicit platform service consumption semantics on PlatformContext: require_scheduler(), require_clock(), require_timer() and require_watchdog() return Result<T*> that succeeds with the adapter-owned, non-owning, non-null service pointer (the same pointer the accessor returns) and otherwise fails with ErrorCode::UNSUPPORTED, ErrorSeverity::ERROR and no component source when the context is unattached or the adapter does not provide the service, in a message that names the service and whether no platform is attached or the platform does not provide it, deterministically and independently for each service; requiring a service is a query that makes exactly one accessor call, never starts, stops, configures, creates or owns a service, never opens hardware and changes no state, and nothing is started or stopped implicitly or when a context is copied or destroyed; platform service errors are never translated, wrapped or rewritten by Core, an Error a service returns keeps its code, severity and message and the only Error Core itself produces is the UNSUPPORTED above, a Component that propagates a platform Error sets the Error's source to its own ComponentId and leaves its code and message unchanged and the Runtime propagates it unchanged under the R0.3 failure semantics, and no error-wrapping helper is added; callback, context-lifetime and re-entry rules remain exactly those of the R0.4 service contracts, and the context stays one pointer with no added state; PlatformRequirements and check_required() remain the way to check several needs before use; no R0.4 signature changes.
- CORE-RT-001 Define the platform-independent lifecycle-managed component contract: immutable component identity (ComponentId, valid iff non-zero) and metadata (ComponentInfo: id, non-empty name, version) fixed at construction; explicit lifecycle operation semantics that reuse the Core lifecycle states and transition table (no new state); Result/Error integration in which every Error returned by an instantiated component's operation is attributable (source is the component id); non-owning lifetime (Core never owns, copies or moves components); and no universal thread-safety or real-time guarantee.
- CORE-RT-002 Define runtime contract.
- CORE-RT-003 Provide a deterministic, non-owning component registry keyed by ComponentId: registration rejects a duplicate id without replacing the existing entry (INVALID_ARGUMENT, source = the id), lookup returns the registered component or nullptr, and enumeration returns each component exactly once in ascending ComponentId order independent of registration order. The registry never owns, copies, moves or deletes a component, never calls a component, has no unregister operation, and is not thread-safe.
- CORE-RT-004 Represent component dependencies by stable ComponentId in a DependencyGraph that holds no component or pointer: self dependencies, duplicate edges (rejected, never merged) and invalid ids are rejected with INVALID_ARGUMENT (source = the dependent) and leave the graph unchanged.
- CORE-RT-005 Detect dependency cycles and provide a deterministic dependency order: an edge that would create a cycle is rejected with the cycle identified in the error, so the graph is always acyclic; order(registry) returns every registered component exactly once, dependencies first, with ties broken by lowest ComponentId (independent of registration and insertion order); an edge endpoint that is not registered fails order() with CONFIGURATION_ERROR and no order is returned. The graph never calls a component.
- CORE-RT-006 Provide a concrete, synchronous Runtime Manager (runtime::RuntimeManager) that implements the existing runtime::Runtime contract (CORE-RT-002) without a competing runtime abstraction: it composes the non-owning ComponentRegistry and the DependencyGraph and forwards setup results unchanged; the first successful initialize() validates the topology with DependencyGraph::order() and permanently fixes it, after which register_component() and add_dependency() fail with INVALID_STATE and change nothing; a failed validation returns the graph's error unchanged, leaves the runtime UNKNOWN and keeps the topology mutable; component order is inherited from DependencyGraph (dependencies first, lowest ComponentId tie-break); its own state follows the Core lifecycle table (initialize UNKNOWN/STOPPED to READY, start READY to RUNNING, stop READY/RUNNING to STOPPED, shutdown a no-op in UNKNOWN/STOPPED, any other call INVALID_STATE with no effect); it never owns, copies or deletes a component (the invocation of component lifecycle operations is specified separately from this requirement), creates no thread or background execution, and is not thread-safe.
- CORE-RT-007 Provide deterministic, dependency-aware runtime lifecycle orchestration in RuntimeManager over the Component lifecycle contract: each Runtime operation first checks the runtime's own state (initialize UNKNOWN/STOPPED to READY, start READY to RUNNING, stop READY/RUNNING to STOPPED, shutdown a no-op in UNKNOWN/STOPPED; configure(Configuration) valid in UNKNOWN/STOPPED with no state change and no topology fixing) and any other call fails with INVALID_STATE having no effect and invoking no component; valid calls invoke the matching Component operation once per component, configure/initialize/start in dependency order and stop/shutdown in the exact reverse order, and the runtime state changes only after the whole sequence succeeded (never READY or RUNNING early); the first failing component ends the sequence with no retry and no rollback and its own Error is returned unchanged; a failed configure or shutdown leaves the state unchanged and a failed initialize, start or stop moves the runtime to FAULT, in which every operation other than explicit recovery (specified separately) fails with INVALID_STATE; the runtime records each component's lifecycle progress itself so a component whose shutdown already succeeded is never shut down again in the same live period and a failed shutdown retried resumes with the failing component; the runtime invokes only the orchestrated operation, never reads or changes component state itself, and performs no automatic retry, background work or threading.
- CORE-RT-008 Provide deterministic runtime failure propagation and explicit, caller-driven recovery in RuntimeManager: a failed component operation is returned unchanged (code, severity, source = the component id, message) and never replaced by a generic runtime error; the runtime records each component's lifecycle progress itself per live period (none, initialized, started, stopped, faulted, shut down), never reading component state or health, and records a failed component as faulted, never as completed; a failed initialize, start or stop moves the runtime to FAULT and fault_error() returns the original causing Error (non-null while the runtime is FAULT, referring to runtime-owned storage that stays valid until a successful reset() clears it or the runtime is destroyed, and nullptr otherwise); in FAULT every operation other than reset() fails with INVALID_STATE and invokes nothing; reset() is the only way out of FAULT, is valid only in FAULT (otherwise INVALID_STATE with no effect and no invocation), never retries the failed operation, and cleans up in two passes each in reverse dependency order (stop every component recorded initialized or started, then shut down every component recorded stopped or faulted, leaving never-invoked components untouched); a successful reset() ends the live period, clears the fault and leaves the runtime STOPPED, with no RECOVERING state used, and the caller must call initialize() explicitly for a new lifecycle attempt; a failed cleanup step returns that component's own Error unchanged, keeps the runtime FAULT with the original fault_error(), preserves progress (a failed stop is recorded as faulted so it is shut down, not stopped again) and a later reset() resumes without repeating a successful step; the runtime owns a Statistics in which sample_count counts component lifecycle invocations that actually returned success, error_count counts those that returned failure (including cleanup), retry_count is never incremented and the remaining fields are unused; error, fault state, health, warning (no warning API), diagnostic, event and message are distinct, component health never triggers recovery, and no automatic retry, background recovery, watchdog, timer or thread exists.
- CORE-RT-009 Demonstrate the integrated Component, ComponentRegistry, DependencyGraph and RuntimeManager implementation against the frozen runtime contract through deterministic, platform-independent integration tests that use only public APIs, reference components and test-only fault injection: complete lifecycle across live periods, dependency branches, registration and edge-insertion order independence, invalid operations, failure propagation, fail-fast, FAULT and reset with two-pass reverse cleanup and resumed cleanup, topology freeze, statistics accounting, non-owning lifetime, and independence from health and background activity, including a seeded model-based comparison of every result, invocation trace, state, fault and statistic with an independent model of the contract; the tests add no production API or behavior.
- CORE-RT-010 Validate the R03 release candidate as a deliverable: a fresh clone builds in Debug and Release with no warnings and passes the complete CTest suite, AddressSanitizer and UndefinedBehaviorSanitizer, ThreadSanitizer where configured, strict compiler diagnostics and GCC -fanalyzer; coverage is reviewed; the requirements traceability audit reports zero errors; the installed package is consumed by an external project at the version recorded in VERSION and CMakeLists.txt; VERSION and the CMake project version agree; no threading, logging or platform-specific dependency is present in the production sources; and the production code is unchanged between the Integration Freeze and the release candidate.

### Foundation types
- CORE-TYP-001 Provide a strong 64-bit identity type; value 0 is the invalid identity.
- CORE-TYP-002 Provide a Version type (major.minor.patch) with string formatting.
- CORE-TYP-003 Provide a nanosecond-resolution Duration type.
- CORE-TYP-004 Provide string key/value Metadata.
- CORE-TIME-001 Provide Timestamp (nanoseconds + clock domain) and the platform-neutral clock abstraction (time::IClock). time::IClock is the canonical clock contract; each clock instance has one fixed domain (MONOTONIC: non-decreasing, unspecified epoch; REALTIME: wall clock that may step). Timestamps from different domains are incomparable: equality includes the domain and Timestamp has no ordering or subtraction. platform::IClock is a compatibility alias of the same type, not a second abstraction. Thread-safety of now() is adapter-defined.
- CORE-TIME-002 Define platform-neutral timer abstraction.

- CORE-LIF-001 Define lifecycle states.
- CORE-STA-001 Define status codes and a Status (code + message) type.
- CORE-HEA-001 Define health states.
- CORE-HEA-002 Provide a Health type reporting a health state.

### Statistics
- CORE-STS-001 Provide a Counter (monotonic unsigned, wraps modulo 2^64 on overflow; not thread-safe, no allocation).
- CORE-STS-002 Provide a Gauge (signed instantaneous value stored as-is, no clamping; not thread-safe, no allocation).
- CORE-STS-003 Provide a Statistics aggregate of common operational counters and gauges with documented field meanings (utilization is a whole percent by convention); not thread-safe, not an atomic snapshot.

### Error and result
- CORE-ERR-001 Define error codes and severities.
- CORE-ERR-002 Define the Error record (code, severity, source, timestamp, message).
- CORE-ERR-003 Reserved (unused).
- CORE-ERR-004 Provide Result<T>/Result<void> with documented access preconditions: value() only on success, error() only on failure, and failure() only with a non-NONE error code. Precondition violations are asserted in debug builds and undefined behavior in release builds; moved-from Results keep their outcome with an unspecified payload.
